# hexad: the differentiable-engine runner

One Rust crate, two products, both shipped in the Linux wheel's `hexcore/libexec`
(`hexcore.hexad` locates them):

| product | what it is |
|---|---|
| `ad-binder` | The runner. `replay` re-executes a recorded forecast step by step from its plan package, on the GPU, with every carried allocation hashed against the ordinary forward. `window` runs the composed tangent-linear model and its exact transpose (the adjoint) over a window of steps, with dot-product, zero-direction and Taylor checks. `capture-dot` and `capdot` check one derivative rule on one captured launch. |
| `libhexad_phys.so` | The same runner behind the libhexad-phys C ABI (v2): a host program hands it device pointers and gets the tangent and adjoint of the physics window without linking Rust. |

`ad-binder --version` prints the crate version, the source commit of the copy and whether the
rule/support fatbins are compiled in.

## Build

```bash
NVCC=/path/to/nvcc cargo build --release --locked --bin ad-binder
NVCC=/path/to/nvcc cargo build --release --locked --lib --features capi-exports --target-dir target-capi
```

`setup.py` runs exactly these two builds while building the wheel (`BuildPy.build_hexad`) and finds
nvcc from `$NVCC`, then `PATH`, then an installed `nvidia-cuda-nvcc` wheel.

- `build.rs` compiles the forecast engine's own plain-stream submitter
  (`src/hexcore/native/step_submit.c`) and refuses unless it has the pinned sha256, so a replay
  submits work exactly as the forecast does. It also compiles the CuPy CUB / Thrust host bridges.
- The four rule and support fatbins (`cuda/*.cu`) are compiled with strict numerics
  (`--fmad=false --prec-div=true --prec-sqrt=true`) for sm_120 and sm_89 SASS plus compute_80
  PTX, which the driver JITs for other cards. `HEXAD_FATBIN_DIR` may name prebuilt images instead.
  With neither, the images are empty: `replay` still works, while `window` and the C ABI refuse at
  module load. A release build sets `GPUWM_HEX_REQUIRE_AD_FATBINS=1`, which turns that case into a
  build error.
- The executable is built without `capi-exports`, and the library with it, because the library must
  export the CUB / Thrust allocator symbols itself (`src/runner/capi_exports.rs`).
- Runtime needs: an NVIDIA driver (`libcuda.so.1` is opened at run time), glibc and libstdc++. No
  CUDA toolkit is needed at run time.

## Layout

- `src/runner/` holds the runner: plan, replay, window, rules and schemes, the C ABI.
- `src/e2e/` holds the ad.entry/v1 binding, device helpers, dots and the held manifest.
- `src/p8/` holds the copy-row plan, rules and rows.
- `cuda/` holds the rule and support kernels.
- `fixtures/` holds the small cubins the replay uses to hash device memory.
- `include/hexad_phys.h` is the C ABI's header. The wheel also ships it as `hexcore/include/hexad_phys.h`.
- `tests/data/` holds the frame samples and held-row specs the unit tests read.

These directories (and `include/`) and `SYNC.json` are generated by a mechanical sync from the autodiff program's
source tree. It copies every file byte for byte, then makes three kinds of change: it rewrites the
module paths, adds `--version`, and replaces internal machine and lane names in comments.
`SYNC.json` records the source commit and each file's sha256 before and after the sync. The
generated directories are not edited by hand, with two exceptions. The release wording of comments, two error
messages, one receipt line, a thread name, a test variable and one test fixture path was reworded after the sync by a rule list (their
public sha256 in `SYNC.json` are the reworded files'). And a file changed on the release line after the sync (an
engine change laid over the synced file) is marked `"edited_after_sync": true` in `SYNC.json`, with the sha256 of
the file as it is here; a unit test compares every entry with its file. `Cargo.toml`, `Cargo.lock`, `build.rs`,
this README and `NOTICE` belong to this crate.

`cargo test --release --locked --bin ad-binder` runs the unit tests.
